# ТЗ: серверный Fabric-мод «Nations & Wars» (планшет наций, территории, войны, дипломатия)

## 0. Контекст для разработчика/ИИ
Это техническое задание на разработку **полноценного серверного Fabric-мода** (не датапак и не только ресурс-пак — логика требует Java-кода). Ресурс-пак с текстурами будет прислан отдельно позже; часть текстур нужно будет создать с нуля по списку в разделе 9 и передать заказчику для интеграции в ресурс-пак. Античит/автозащита блоков на чужой территории **не реализуется** — территория чисто административно-политическая сущность (для войн, налогов, разметки), физической защиты блоков нет.

---

## 1. Стек и требования
- **Loader:** Fabric (актуальная стабильная версия под целевую версию игры, уточнить у заказчика — например 1.20.x/1.21.x).
- **API:** Fabric API обязателен.
- **Хранение данных:** `PersistentState` (привязка к миру/серверу), сериализация в NBT или JSON (JSON предпочтительнее — легче дебажить и делать бэкапы).
- **Сеть:** кастомные пакеты через `ServerPlayNetworking` / `ClientPlayNetworking` (Fabric Networking API v1).
- **GUI:** кастомные `ScreenHandler` + `HandledScreen` (не стандартный инвентарь, а полноценные кастомные экраны с кнопками/текстовыми полями).
- **Совместимость с картами:** BlueMap (имеет нативный Fabric-модуль) — приоритет; Dynmap на Fabric поддерживается хуже, рассматривать как опциональную интеграцию через API, если доступен Fabric-порт.

## 2. Предмет «Планшет наций» (Tablet)
### 2.1 Крафт
Верстак 3×3:
```
[ ] [Redstone] [ ]
[Redstone] [Iron Ingot] [Redstone]
[ ] [Redstone] [ ]
```
Реализовать как обычный shaped-рецепт через data pack JSON (`recipe/nations_tablet.json`), результат — кастомный `Item` с уникальной моделью/текстурой.

### 2.2 Поведение
- ПКМ (правый клик) в воздухе или по блоку → открывает главное меню (см. раздел 3).
- Предмет невозможно скрафтить дубликатом сверх одного на игрока (опционально — ограничение через NBT-метку «уже привязан к профилю» либо разрешить свободный крафт, уточнить у заказчика).

## 3. Структура GUI (меню планшета)

### 3.1 Главное меню
Кнопки:
1. **Создать страну** (Create Nation)
2. **Создать город** (Create City)
3. **Разметить территорию** (Claim Territory)
4. **Моя страна/город** (управление, если состоишь)
5. **Список стран/городов** (реестр всех зарегистрированных)
6. **Дипломатия** (войны, союзы, входящие запросы)
7. **Уведомления** (входящие запросы: войны, вступление в страну)

### 3.2 Создание страны/города
- Текстовое поле: название (уникальность проверяется на сервере, регистр не важен).
- Выбор цвета территории (см. 4.2) — либо рандомная выдача, либо выбор из палитры, если свободен.
- Кнопка «Создать» → списывает стоимость создания (если решите ввести — уточнить у заказчика цену в алмазах/др. валюте, либо бесплатно).
- После создания — сразу переход к экрану разметки территории.

### 3.3 Разметка территории
- Логика: игрок закрывает GUI, встаёт на первый угол участка, ПКМ по планшету с зажатым Shift (или отдельная кнопка «Отметить точку А/Б» в GUI, которая переводит в «режим разметки» — игрок кликает по земле деревянным маркером/призрачными частицами).
- Рекомендуемая единица измерения — **чанк (16×16)**, а не произвольный блок, это радикально упрощает пересечения территорий и рендер на карте. 500 блоков ≈ 2 чанка. Предложить заказчику округлить лимит до «2 чанка бесплатно / +2 чанка за 15 алмазов» либо оставить точный подсчёт блоков через полигон (сложнее в реализации и в проверке пересечений).
- Визуализация выделенной территории — подсветка границ частицами (`ServerWorld#spawnParticles`) цветом нации, никакого влияния на текстуры чужих блоков (ресурс-пак не умеет красить блоки в реальном времени).
- Проверка пересечений с чужими территориями — обязательна, отказ с сообщением, если участок уже занят.
- Лимит 500 блоков (или N чанков) бесплатно. При превышении — экран подтверждения списания 15 алмазов за каждые +500 блоков (или +2 чанка), рекурсивно (можно доплачивать многократно).

### 3.4 Управление страной/городом
- Список участников, их роли.
- Кнопка «Назначить роль» (см. раздел 6).
- Кнопка «Исключить игрока».
- Кнопка «Правила» — текстовое поле, свободный ввод правил (просто хранится как строка/список строк, отображается всем участникам или всем игрокам при заходе на территорию — опционально через title/actionbar).
- Кнопка «Казна» — баланс, история последних операций.
- Кнопка «Присоединить город к стране» (только для лидеров городов) — отправка заявки лидеру страны.
- Кнопка «Распустить» (удалить страну/город, с подтверждением).

### 3.5 Дипломатия и войны
- **Список зарегистрированных стран/городов** с возможностью:
  - «Объявить войну» → выбор типа войны (см. 7.2) → подтверждение → отправка пакета-уведомления лидеру цели.
  - «Предложить союз» / «Пакт о ненападении» / «Торговое соглашение».
- **Входящие запросы** (обязательный экран-уведомление, всплывающее при входе в игру или при открытии планшета, плюс toast-сообщение в момент отправки):
  - Война: «Страна X объявила вам войну» → [Принять] [Отклонить].
  - Вступление города в страну: «Город Y хочет войти в состав вашей страны» → [Принять] [Отклонить].
  - Союз/пакт: аналогично.

## 4. Модель данных

### 4.1 Основные сущности (классы)
- `Nation` — id, название, лидер (UUID), список участников+роли, казна, репутация, список городов, список территорий (чанки), правила (строки), список войн/союзов/пактов.
- `City` — id, название, лидер (UUID), участники+роли, казна, территория (чанки), правила, ссылка на `Nation` (nullable, если независим).
- `Claim` — координаты чанка, привязка к `Nation`/`City`, цвет.
- `War` — id, инициатор, цель, тип войны, статус (pending/active/finished), таймстемпы, результат.
- `DiplomaticRelation` — пара сторон, тип (союз/пакт/торговля), статус.
- `PlayerProfile` — UUID, роль в текущей организации, репутация, история.

### 4.2 Цвет территории
- При создании страны/города сервер выдаёт случайный цвет из заранее заданной палитры (например 16–32 контрастных цвета), не повторяющийся среди активных организаций. Цвет используется:
  - в частицах при разметке;
  - в GUI (значок организации);
  - на карте (BlueMap-маркер областей — см. раздел 8).

### 4.3 Персистентность
- Все данные хранить в одном `PersistentState`, сериализация в JSON-файл (`world/data/nations.json` или NBT — на усмотрение реализации), с бэкапом при сохранении мира.

## 5. Экономика
- Валюта — алмазы (можно брать напрямую предметы `minecraft:diamond` из инвентаря игрока при подтверждении траты) либо абстрактный баланс в казне организации, пополняемый вручную (игрок кладёт алмазы в специальный слот GUI «Казна» → конвертируются в баланс).
- Расширение территории — 15 алмазов за каждые +500 блоков/+2 чанка.
- (Рекомендация, обсудить с заказчиком) — периодический налог на землю: списание из казны раз в игровые сутки, пропорционально площади; при недостатке средств — территория помечается как «в долге», через N дней автоматически разморожена (снята с учёта), чтобы не копились заброшенные страны.
- Казна тратится на: расширение территории, оплату войн (см. 7), возможно — future-фичи (бонусы, посольства).

---

## 6. Роли и права
Минимальный набор ролей (кастомизируемый лидером):
- **Лидер** — все права, не может быть исключён, может передать лидерство.
- **Заместитель/Министр** — приглашать, исключать (кроме лидера), объявлять войну, тратить казну (лимит настраивается).
- **Участник** — базовые права (строить на территории, если это разрешено политикой организации — но без античита это чисто декларативно).
- **Гость/Вассал** (для городов-вассалов внутри страны) — ограниченные права.

Права реализовать как битовую маску/enum-набор (`Permission.INVITE`, `Permission.KICK`, `Permission.DECLARE_WAR`, `Permission.SPEND_TREASURY`, `Permission.EDIT_RULES`, `Permission.MANAGE_CLAIMS`), лидер назначает набор прав каждой роли через GUI.

## 7. Война

### 7.1 Объявление войны
- Инициатор выбирает цель из реестра → выбирает тип войны → подтверждает.
- Цели отправляется пакет + всплывающее окно с описанием условий войны и кнопками Принять/Отклонить.
- Если цель отклоняет — по умолчанию либо война отменяется, либо (опционально) инициатор обязан ждать cooldown перед повторным объявлением. Уточнить у заказчика, возможна ли «безусловная» война (без права отказа) как отдельный, более агрессивный режим.

### 7.2 Типы войны (рекомендация)
1. **Аннексия** — победитель забирает спорные чанки территории в свою собственность.
2. **Вассализация** — проигравший сохраняет территорию, но обязан выплачивать периодическую дань победителю (запись в `DiplomaticRelation` типа VASSAL).
3. **Контрибуция (грабёж)** — победитель получает единоразовую выплату из казны проигравшего.

### 7.3 Определение победителя
Так как античит/защита блоков не реализуется, победа определяется одним из способов (обсудить с заказчиком, что проще для вашей аудитории):
- **По очкам убийств** участников враждующих сторон за период войны (таймер, например 3–7 игровых дней), финальный подсчёт — авто.
- **По удержанию контрольной точки** в спорном чанке (маячок/блок, отслеживание нахождения игроков рядом определённое время).
- **Ручное завершение** лидерами (кнопка «Признать поражение» / «Заявить победу», с возможностью оспорить администрацией сервера — самый простой вариант для MVP).

Рекомендация для первой версии мода: сделать **ручное завершение + таймер автоотмены**, а очковую/осадную систему добавить позже, когда будет обратная связь от игроков.

## 8. Дипломатия
- **Союз** — взаимная защита (чисто декларативно, отображается в GUI и, опционально, не позволяет объявить войну союзнику без предварительного разрыва союза).
- **Пакт о ненападении** — блокирует кнопку «Объявить войну» между сторонами, пока пакт активен; разрыв — с cooldown (например, 24 часа предупреждения).
- **Торговое соглашение** — заготовка на будущее (скидки/бонусы), в MVP можно ограничиться просто флагом «есть соглашение» без реальной механики.
- **Посольство** (доп. фича, см. раздел 10) — отдельный клейм внутри чужой территории.

4. **Фон экрана разметки территории** (индикатор занятых/свободных блоков, счётчик лимита 500/1000 и т.д., кнопка доплаты алмазами).
5. **Фон экрана управления организацией** (список участников, роли, кнопки назначения).
6. **Фон экрана казны** (баланс, слот для внесения алмазов, история операций).
7. **Фон экрана дипломатии/войны** (список организаций, кнопки Объявить войну/Союз/Пакт).

9. **Иконки ролей** (корона — лидер, звезда — министр, обычная — участник).
10. **Значки-маркеры территорий для карты** (см. раздел 10) — по одному на цвет палитры, для использования в BlueMap markers API.

Все текстуры — в стилистике ванильного Minecraft GUI (можно на основе `textures/gui/container/generic_54.png` как референс пропорций) либо в отдельном фирменном стиле — уточнить у заказчика предпочтения (тёмный/светный, пиксель-арт уровень детализации).

## 10. Интеграция с картами (BlueMap / Dynmap)

### 10.1 BlueMap (приоритетно)
- BlueMap имеет официальную поддержку Fabric (мод устанавливается на сервер отдельно, слушает через свой Java API `BlueMapAPI`).
- Наш мод должен **опционально** зависеть от BlueMap (soft-depend): при старте сервера проверяем, зарегистрирован ли `BlueMapAPI.getInstance()`.
- Если BlueMap найден — при каждом изменении территорий (создание/удаление/расширение) обновляем `MarkerSet`:
  - Полигон (`ShapeMarker`) по границам чанков организации, заливка цветом её палитры (полупрозрачная заливка + контрастная обводка).
  - Подпись с названием страны/города и (опционально) лидером.
- Если BlueMap не найден на сервере — интеграция просто отключается без ошибок (проверка через `FabricLoader.getInstance().isModLoaded("bluemap")`).

### 10.2 Dynmap
- Dynmap исторически Bukkit/Spigot-плагин; Fabric-порты существуют, но менее стабильны и с ограниченным API. Реализовать как **опциональный** модуль по тому же принципу soft-depend, но с более низким приоритетом разработки — сначала полностью сделать BlueMap-интеграцию, Dynmap добавить второй итерацией, если на сервере он реально будет использоваться.

### 10.3 Общая архитектура интеграции
Вынести рендер территорий в отдельный интерфейс `MapProvider` с реализациями `BlueMapProvider`, `DynmapProvider` (заглушка/будущее), чтобы ядро мода (Nation/City/Claim логика) не зависело напрямую от конкретной карты — легко добавить новую карту позже.

## 11. Дополнительные механики (рекомендованные, обсудить приоритет)
- Казна с общим вкладом участников.
- Гранулярные права по ролям (раздел 6).
- Репутация организации — падает от частых необоснованных войн, влияет на возможность заключать союзы (например, ниже порога — союзники отказываются автоматически или требуется подтверждение с предупреждением).
- Голосование за нового лидера при długой офлайн-активности текущего (например, 14+ дней) — участники с правом голоса выбирают преемника через GUI-голосование.
- Ресурсные бонусы за биом территории (например, +к скорости добычи в шахтёрских биомах) — опционально, через `AttributeModifier`, активный только пока игрок находится в чанке своей организации.
- Торговые пути — бонус, если города соединены дорогой/договором (в MVP можно не делать, отметить как «фаза 2»).
- Посольства — отдельный небольшой клейм-исключение внутри чужой территории со статусом неприкосновенности (просто отдельный `Claim` с флагом `isEmbassy`, привязанный к другой организации).

## 12. Приоритеты разработки (предложенная последовательность)
1. Предмет-планшет + крафт + базовый ПКМ → пустое меню-заглушка.
2. Data-модель Nation/City/Claim + PersistentState (сохранение/загрузка).
3. GUI: создание страны/города, разметка территории (чанки), лимит 500 блоков + доплата алмазами.
4. Управление организацией: роли, права, казна, правила.
5. Реестр организаций + вступление города в страну (заявки).
6. Дипломатия: войны (объявление/принятие/ручное завершение), союзы, пакты.
7. Уведомления (toast + экран входящих запросов).
8. Интеграция BlueMap (полигоны территорий).
9. Ресурс-пак: текстуры по списку раздела 9 (создаются отдельно и присылаются заказчику для сборки в финальный пак вместе с его собственным ресурс-паком).
10. (Фаза 2) Dynmap, репутация, голосования, ресурсные бонусы, торговые пути, посольства.

## 14. Порядок работы ИИ-исполнителя (обязательно к соблюдению)

- **Сначала действия, потом текст.** ИИ не описывает план в чате перед работой — он сразу пишет/редактирует код, создаёт файлы, настраивает конфигурацию, генерирует рецепты/модели и т.д. Сообщение пользователю пишется только после того, как реальные изменения внесены.
- **Каждый этап из раздела 12 доводится до рабочего состояния**, прежде чем ИИ переходит к следующему: код должен не просто существовать, а собираться.
- **Обязательная самостоятельная компиляция.** После внесения изменений ИИ сам запускает сборку проекта (`./gradlew build` или как минимум `./gradlew compileJava`) без запроса разрешения. Билд — часть выполнения задачи, а не отдельный шаг, который нужно попросить.
- **Самостоятельное исправление ошибок.** Если сборка падает — ИИ анализирует лог, исправляет код и пересобирает проект повторно, циклически, пока не получит успешный билд. Пользователя не спрашивают на каждой ошибке компиляции; вопросы задаются, только если ошибка связана с открытым вопросом из раздела 13 (например, неясная версия Fabric/Minecraft), либо если несколько разумных попыток исправления не дали результата.
- **Отчёт в конце, а не в процессе.** После успешной сборки (или после исчерпания разумного числа попыток) ИИ даёт короткий итоговый отчёт: что реализовано, что скомпилировано и прошло базовую проверку, какие пункты из раздела 13 требуют уточнения у заказчика. Никаких пересказов промежуточных рассуждений или списков «что я сейчас буду делать» — только результат.
- Если для сборки нужны внешние зависимости или файлы, которых нет в окружении (например, реальный Fabric API/Loom-конфигурация, недоступная офлайн), ИИ отмечает это прямо в итоговом отчёте как ограничение окружения, а не как повод остановиться до начала работы.
- **Отчёт без артефактов не считается выполнением.** Список из галочек «✅ сделал то, ✅ сделал это» без приложенных реальных результатов — это не отчёт о выполнении, а пересказ намерений, и такой ответ недопустим. К каждому итоговому сообщению должно быть приложено хотя бы одно из:
  - реальные файлы проекта (архив, отдельные файлы кода, `build.gradle`, дерево каталогов) — доступные для скачивания/просмотра, а не только текст «я создал файл X»;
  - реальный вывод команды сборки (`./gradlew build` / `./gradlew compileJava`) — фрагмент лога, включая либо `BUILD SUCCESSFUL`, либо конкретные ошибки компиляции с исправлением;
  - если инструмент/среда, в которой работает ИИ, физически не может исполнять код или создавать файлы (нет песочницы, нет доступа к файловой системе) — ИИ обязан прямо сообщить об этом ограничении явным текстом («у меня нет доступа к среде исполнения/файлам, я могу только сгенерировать код текстом») вместо того, чтобы описывать несуществующие действия как выполненные.
- Формулировки-имитации процесса («проверяю Gradle…», «делаю то-то…», списки с ✅ без результата) без реального артефакта расцениваются как невыполнение задачи, и работа считается не начатой, даже если текст выглядит уверенно и подробно.
